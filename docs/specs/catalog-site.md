# Специфікація: сайт-каталог маркетплейсу на GitHub Pages

Статус: узгоджено, готово до реалізації · Дата: 2026-10-20

## 1. Мета

Статичний сайт на GitHub Pages, де користувач знаходить потрібний плагін, скіл чи агента з маркетплейсу `dev-digest-toolkit` і одразу встановлює його. Бекенду немає: усе, що потребує обробки даних, виконується під час збірки в GitHub Actions, а сайт у браузері лише читає згенеровані JSON-файли.

### Поза обсягом

Семантичний (векторний) пошук, кошик зі збіркою `settings.json`, панель безпеки, тестер тригерів, генератор плагіна, будь-яка серверна логіка, авторизація, збір аналітики.

## 2. Обмеження та передумови

- **GitHub Pages віддає лише статику.** Немає серверного коду, змінних середовища в рантаймі, серверних редиректів і SPA-fallback. Маршрутизація — через hash (`#/…`).
- **Сайт публічний**, як і репозиторій. Весь вміст `plugins/` (README, тіла скілів і агентів) потрапляє на сайт.
- **Адреса**: `https://mshcherbyna.github.io/dev-digest-toolkit-marketplace/`, тому у Vite `base: '/dev-digest-toolkit-marketplace/'`.
- **Жодних запитів до GitHub API з браузера.** Неавторизований ліміт — 60 запитів/год на IP. Усі дані з git і GitHub (теги, дати) отримуємо під час збірки.
- **Каталог зараз порожній** (`plugins: []`). Сайт має коректно працювати з нулем плагінів (див. [§5.7](#57-порожні-стани)).

## 3. Архітектура

```
push у main ──► .github/workflows/pages.yml
                 │
                 ├─ node scripts/build-catalog.mjs
                 │     читає .claude-plugin/marketplace.json, plugins/*/…, git-теги
                 │     пише site/public/data/catalog.json
                 │          site/public/data/search-index.json
                 │
                 ├─ npm ci && npm run build   (у site/)
                 │
                 └─ actions/upload-pages-artifact → actions/deploy-pages
```

### 3.1 Розміщення в репозиторії

```
scripts/
  build-catalog.mjs        # генератор даних (нова)
  lib/plugin-files.mjs     # спільний парсинг для валідатора й генератора (винесено з validate-marketplace.mjs)
site/
  package.json + package-lock.json
  index.html
  src/…
  public/data/             # генерується, у .gitignore
.github/workflows/pages.yml
```

`parseFrontmatter`, `walk`, `readJson` з `validate-marketplace.mjs` виносимо в `scripts/lib/plugin-files.mjs`, щоб валідатор і генератор розбирали файли однаково. Після цього валідатор має поводитися як раніше (регресійна перевірка: той самий вивід на поточному репозиторії).

### 3.2 Стек

- **Vite + Preact + TypeScript.** Малий бандл, звичні інструменти, без SSR. Залежності — з точними версіями в `package-lock.json`, як того вимагає CONTRIBUTING.
- **MiniSearch** — повнотекстовий пошук у браузері. Індекс серіалізується під час збірки (`JSON.stringify(miniSearch)`) і завантажується через `MiniSearch.loadJSON`, тож у браузері нічого не індексується.
- **Markdown** рендериться в HTML під час збірки (`marked`) і санітизується (`sanitize-html`, allowlist тегів). Браузер отримує вже готовий безпечний HTML.
- Генератор `build-catalog.mjs` використовує лише `node:` модулі плюс `marked`/`sanitize-html`/`minisearch`. Їх ставимо з `site/package-lock.json`, щоб не створювати ще один `package.json` у корені.

## 4. Модель даних

### 4.1 Артефакти

Індексуємо кожен компонент окремо, щоб на запит «скіл для X» знаходився саме скіл, а не лише плагін, який його містить.

| `type` | Джерело | Поля |
|---|---|---|
| `plugin` | запис у `marketplace.json` + `plugin.json` + `README.md` | name, displayName, description, version, author, license, homepage, keywords, category, tags, dependencies |
| `skill` | `skills/<skill>/SKILL.md` | frontmatter `name`, `description`, `allowed-tools` та інші поля; тіло |
| `agent` | `agents/*.md` | frontmatter `name`, `description`, `tools`, `model`; тіло |
| `command` | `commands/*.md` | ім'я файлу, frontmatter `description`, `argument-hint`; тіло |
| `hook` | `hooks/hooks.json` | подія (`PreToolUse`, …), `matcher`, команда |
| `mcp` | `.mcp.json` | назва сервера, тип (stdio / http / sse), `command` або `url` |

### 4.2 `catalog.json`

```jsonc
{
  "schemaVersion": 1,
  "generatedAt": "2026-10-20T12:00:00Z",
  "commit": "abc1234",
  "marketplace": {
    "name": "dev-digest-toolkit",
    "repo": "MShcherbyna/dev-digest-toolkit-marketplace",   // з GITHUB_REPOSITORY у CI
    "description": "…"
  },
  "stats": { "plugins": 0, "skills": 0, "agents": 0, "commands": 0, "hooks": 0, "mcp": 0 },
  "plugins": [
    {
      "name": "pr-review",
      "displayName": "PR Review",
      "description": "…",
      "version": "1.2.0",
      "author": { "name": "…" },
      "license": "MIT",
      "keywords": ["review", "рев'ю"],
      "category": "…",
      "dependencies": [],
      "install": "/plugin install pr-review@dev-digest-toolkit",
      "sourceUrl": "https://github.com/<repo>/tree/main/plugins/pr-review",
      "readmeHtml": "<h1>…</h1>",
      "components": [
        {
          "id": "pr-review/skill/review-diff",
          "type": "skill",
          "name": "review-diff",
          "description": "…",
          "meta": { "allowed-tools": "Read, Grep" },
          "bodyHtml": "…",
          "sourceUrl": "https://github.com/<repo>/blob/main/plugins/pr-review/skills/review-diff/SKILL.md"
        }
      ],
      "releases": [
        { "version": "1.2.0", "tag": "pr-review--v1.2.0", "date": "2026-10-01", "notesHtml": "…" }
      ]
    }
  ],
  "releases": [ /* усі релізи всіх плагінів, від нових до старих, до 50 записів */ ]
}
```

`catalog.json` — публічний машиночитний контракт. Змінюючи його структуру несумісно, підвищуємо `schemaVersion`.

### 4.3 Пошуковий індекс

Один документ на артефакт (плагін або компонент):

| Поле | Вага (boost) | Примітка |
|---|---|---|
| `name` | 4 | дефіси й підкреслення також розбиваються на окремі токени |
| `keywords`, `tags` | 3 | з `plugin.json` / запису каталогу; компоненти успадковують keywords свого плагіна |
| `description` | 2 | |
| `body` | 1 | текст без розмітки, обрізаний до 5 000 символів на документ |

Збережені поля (для рендеру картки без завантаження `catalog.json`): `id`, `type`, `name`, `description`, `plugin`.

## 5. Функціональні вимоги

### 5.1 Пошук і картки

**Головна сторінка (`#/`)**: поле пошуку у фокусі, під ним Stats-плитка, What's new (3 останні записи) і сітка карток.

**Обробка запиту** (виконується в браузері до пошуку):
1. Нормалізація: нижній регістр, `ё→е`, апостроф `'`/`’`/`ʼ` → `'`.
2. **Слова типу** перетворюються на фільтр і видаляються із запиту:
   `скіл|скіла|skill|навичк*` → `skill`, `агент*|agent` → `agent`, `хук*|hook` → `hook`, `команд*|command` → `command`, `mcp|сервер*` → `mcp`, `плагін*|plugin` → `plugin`.
3. **Стоп-слова** (UA + EN) видаляються: `мені, треба, потрібно, для, який, яка, щоб, як, і, та, в, на, з, i, need, a, for, to, the, that, which, …`. Список — у `site/src/search/stopwords.ts`.
4. **Синоніми** зі `site/src/search/synonyms.json` розширюють запит (`рев'ю ↔ review`, `тести ↔ tests`, `документація ↔ docs`). Файл редагують у PR, як і будь-який інший.
5. Пошук MiniSearch: `prefix: true`, `fuzzy: 0.2`, `combineWith: 'OR'`, сортування за score. Якщо після кроку 3 не залишилося жодного слова, показуємо всі артефакти вибраного типу.

Приклад: `Мені треба скіл для рев'ю PR` → фільтр `type=skill`, терміни `рев'ю review pr`.

**Фільтри**: чіпи за типом (Усі / Плагіни / Скіли / Агенти / Команди / Хуки / MCP) з кількістю результатів. Фільтр із запиту (крок 2) вмикає відповідний чіп; користувач може його вимкнути.

**URL-стан**: `#/?q=<запит>&type=<тип>`. Оновлюється з debounce 300 мс через `history.replaceState`. Відкриття такого посилання відновлює запит і фільтр.

**Картка** містить:
- бейдж типу (колір + текст, не лише колір);
- назву (`displayName` або `name`);
- для компонента — рядок «у плагіні `<plugin>`»;
- `description`, обрізаний до 3 рядків;
- версію плагіна;
- кнопку **Copy install** ([5.2](#52-copy-install)).

Клік по картці (крім кнопки) відкриває detail-view.

**Критерії приймання**
- [ ] На каталозі з 500 артефактів результати з'являються менш ніж за 50 мс після введення (без урахування debounce 150 мс).
- [ ] Запит `скіл для рев'ю` знаходить скіл, у якого `review` є в назві, description або keywords плагіна.
- [ ] Запит із помилкою в одну літеру (`reviw`) все одно знаходить `review`.
- [ ] Посилання `#/?q=test&type=agent`, відкрите в новій вкладці, показує ті самі результати.
- [ ] Поле пошуку отримує фокус за натисканням `/`; `Esc` очищає запит.

### 5.2 Copy install

- Копіює `/plugin install <plugin>@<marketplace.name>`. Назва маркетплейсу береться з `catalog.json`, а не з коду, тож на сайті не може опинитися застаріла чи хибна назва.
- На картці компонента копіюється команда встановлення його плагіна; у підказці (`title`) пояснюємо, що скіл встановлюється разом із плагіном.
- Після кліку кнопка 2 секунди показує «Скопійовано» (`aria-live="polite"`).
- Якщо Clipboard API недоступний, показуємо команду у виділеному полі для ручного копіювання.

**Критерії приймання**
- [ ] У буфері рівно один рядок, без пробілів на кінцях і переносів рядка.
- [ ] Клік по кнопці не відкриває detail-view.

### 5.3 Detail-view

**Маршрути**
- `#/plugin/<name>` — сторінка плагіна.
- `#/plugin/<name>/<type>/<component>` — сторінка компонента, наприклад `#/plugin/pr-review/skill/review-diff`.
- Невідомий маршрут або плагін → сторінка «Не знайдено» з посиланням на пошук.

**Сторінка плагіна**
- Шапка: назва, версія, автор, ліцензія, кнопка Copy install, посилання «Код на GitHub» (`sourceUrl`) і `homepage`, якщо є.
- **Склад**: компоненти, згруповані за типом, із посиланням на сторінку кожного.
- **Що запускає**: зведення, складене під час збірки:
  - хуки: подія → matcher → команда;
  - MCP-сервери: назва, тип, `command` (для stdio) або `url` (для http/sse);
  - `userConfig`: назви ключів і позначка `sensitive`.
- **Залежності**: `dependencies` з посиланнями на відповідні плагіни каталогу.
- **README**: HTML, відрендерений під час збірки.
- **Історія версій**: `releases` цього плагіна.

**Сторінка компонента**
- Назва, тип, батьківський плагін (посилання), Copy install плагіна.
- Frontmatter таблицею. Для скілів окремо показуємо `allowed-tools`, для агентів — `tools` і `model`.
- Тіло `SKILL.md` або агента як HTML.
- Посилання «Файл на GitHub».

**Безпека рендеру**: увесь HTML із markdown проходить `sanitize-html` під час збірки. Дозволені теги: заголовки, абзаци, списки, `code`/`pre`, таблиці, `a`, `img`, `blockquote`. Заборонені `script`, `style`, `iframe`, обробники подій, `javascript:`-URL. Зовнішні посилання отримують `rel="noopener noreferrer"` і `target="_blank"`. Відносні посилання й зображення переписуються в абсолютні URL на `github.com/<repo>/blob/main/…` і `raw.githubusercontent.com/…` відповідно.

**Критерії приймання**
- [ ] Пряме відкриття `…/#/plugin/<name>` показує сторінку плагіна (без проходження через головну).
- [ ] Кнопка «Назад» у браузері повертає до результатів пошуку з тим самим запитом.
- [ ] `<script>` у README плагіна не потрапляє в DOM.
- [ ] `<title>` сторінки змінюється на `<name> · Dev Digest Toolkit`.

### 5.4 What's new

**Джерело даних** (під час збірки, в порядку пріоритету):
1. Git-теги `<name>--v<version>` (формат з `claude plugin tag`). Дата — дата коміту тега. Для цього в CI потрібен `fetch-depth: 0`.
2. Нотатки до версії — секція `## <version>` або `## [<version>]` із `plugins/<name>/CHANGELOG.md`, якщо файл існує. Інакше — тема повідомлення коміту тега.
3. Якщо тегів немає, але плагін є в каталозі, створюється один запис «Додано» з поточною версією і датою першого коміту, що додав `plugins/<name>/`.

**UI**
- Блок на головній: 3 останні записи.
- Сторінка `#/whats-new`: усі записи (до 50), згруповані за місяцем. Кожен запис: плагін (посилання), версія, дата, позначка «новий плагін» або «оновлення», нотатки (згорнуті, якщо довші за 5 рядків).

**Критерії приймання**
- [ ] Новий тег `foo--v1.1.0` після push з'являється на сайті першим записом.
- [ ] Плагін без тегів і без CHANGELOG показується з записом «Додано».

> Варто розглянути: доповнити `CONTRIBUTING.md` рекомендацією вести `CHANGELOG.md` у плагіні. Без нього нотатки до релізів будуть лише темами комітів.

### 5.5 Stats

Плитка з лічильниками: плагіни · скіли · агенти · команди · хуки · MCP-сервери, плюс «оновлено <дата>» (`generatedAt`). Значення беруться з `catalog.stats`. Клік по лічильнику вмикає відповідний фільтр пошуку. Лічильники зі значенням 0 приховуються, крім «плагіни».

**Критерії приймання**
- [ ] Сума лічильників дорівнює кількості документів у пошуковому індексі.

### 5.6 Онбординг

Сторінка `#/start`, на яку веде помітне посилання «Як підключити» в шапці.

Кроки, кожен з кнопкою копіювання:
1. **Додати маркетплейс**: `/plugin marketplace add <repo>` (у сесії Claude Code) і `claude plugin marketplace add <repo>` (у терміналі) — перемикач-вкладки.
2. **Встановити плагін**: `/plugin install <plugin>@<marketplace>` з випадаючим списком плагінів каталогу. Без вибору показується шаблон `<plugin>`.
3. **Увімкнути автооновлення**: інструкція з README (`/plugin` → Marketplaces → … → Enable auto-update) і команда ручного оновлення.
4. **Для команди**: готовий `.claude/settings.json` з `extraKnownMarketplaces` і `enabledPlugins`, де плагін, вибраний на кроці 2, вже вписаний.
5. **Приватний доступ** (згорнуто): `gh auth login && gh auth setup-git`.

`<repo>` і `<marketplace>` підставляються з `catalog.marketplace`.

**Критерії приймання**
- [ ] Скопійований на кроці 4 JSON проходить `JSON.parse` і містить актуальні назви репозиторію та маркетплейсу.
- [ ] Новий користувач проходить кроки 1–2 без переходу на інші сторінки.

### 5.7 Порожні стани

- **Каталог порожній**: замість сітки — «Плагінів поки немає» і посилання на CONTRIBUTING. Онбординг доступний, Stats показує «0 плагінів», What's new приховано.
- **Немає результатів**: «Нічого не знайшли за запитом «…»», підказка спробувати англійське слово, кнопка «Скинути фільтр» (якщо він увімкнений).
- **`catalog.json` не завантажився**: повідомлення про помилку з кнопкою «Спробувати ще раз»; онбординг працює з типовими значеннями, вбудованими під час збірки.

## 6. Нефункціональні вимоги

- **Продуктивність**: JS-бандл ≤ 60 КБ gzip без даних. `search-index.json` і `catalog.json` завантажуються паралельно; detail-view використовує вже завантажений `catalog.json`. Якщо `catalog.json` перевищить 1 МБ, виносимо `readmeHtml`/`bodyHtml` в окремі файли `data/plugins/<name>.json` (зміна всередині збірки, без нової версії схеми).
- **Без зовнішніх запитів у рантаймі**: ні CDN, ні шрифтів, ні аналітики, ні GitHub API. CSP через `<meta http-equiv="Content-Security-Policy">`: `default-src 'self'; img-src 'self' https://raw.githubusercontent.com data:; style-src 'self'; script-src 'self'`.
- **Доступність**: керування з клавіатури, видимий фокус, контраст WCAG AA, бейджі типу не розрізняються лише кольором, `aria-live` для кількості результатів.
- **Адаптивність**: від 360 px, сітка 1/2/3 колонки.
- **Тема**: світла й темна за `prefers-color-scheme` з перемикачем; вибір зберігається в `localStorage`, а якщо сховище недоступне, береться системна тема.
- **Мова інтерфейсу**: українська. Усі рядки інтерфейсу — в `site/src/i18n/uk.ts`, щоб англійську можна було додати без рефакторингу.

## 7. CI/CD

### 7.1 `.github/workflows/pages.yml`

- Тригери: `push` у `main` зі змінами в `plugins/**`, `.claude-plugin/**`, `site/**`, `scripts/**`; push тегів `*--v*`; `workflow_dispatch`.
- `permissions: { contents: read, pages: write, id-token: write }`, `concurrency: { group: pages, cancel-in-progress: false }`.
- Кроки: `actions/checkout` (`fetch-depth: 0`, для дат тегів) → `actions/setup-node` (22) → `npm ci` у `site/` → `node scripts/build-catalog.mjs` → `npm run build` → `actions/configure-pages` → `actions/upload-pages-artifact` (`site/dist`) → `actions/deploy-pages`.
- Усі actions закріплені за SHA з коментарем-версією, як у `validate.yml`.
- У налаштуваннях репозиторію: Settings → Pages → Source: **GitHub Actions**.

### 7.2 Перевірка в `validate.yml`

Додати job `site`: `build-catalog.mjs` + `npm run build` + юніт-тести (див. [§8](#8-тестування)) на кожен PR. Зламаний генератор чи сайт виявляються до мержу, а не під час деплою. Додати `site` до обов'язкових status checks у ruleset.

### 7.3 Поведінка генератора

- Генератор не валідує: якщо структура плагіна некоректна, це відловлює `validate`. Проте він не падає на відсутніх необов'язкових файлах (README, CHANGELOG, `agents/`), а пише попередження в лог.
- Вивід детермінований (сортування за `name`, стабільний порядок ключів), крім `generatedAt` і `commit`.

## 8. Тестування

- **Генератор** (`node --test`): фікстура `scripts/test/fixtures/marketplace/` з двома плагінами (повний і мінімальний). Перевіряємо `catalog.json`: склад компонентів, stats, release-записи, санітизацію (`<script>` у README зникає), переписування відносних посилань.
- **Пошук** (Vitest): обробка запиту (слова типу, стоп-слова, синоніми) і ранжування на фікстурі — кейси з критеріїв приймання §5.1.
- **E2E** (Playwright, в CI проти `vite preview`): пошук → картка → detail-view → «Назад»; Copy install; deep-link у новій вкладці; порожній каталог.
- **Регресія валідатора**: після винесення спільного коду `validate-marketplace.mjs` дає той самий вивід на репозиторії й фікстурах.

## 9. Ухвалені рішення

1. **Видимість**: репозиторій публічний, сайт теж. Обмежень на публікацію вмісту немає.
2. **Назва маркетплейсу**: `dev-digest-toolkit`. Сайт бере її з `marketplace.json` і ніде не вписує в код.
3. **Двомовні keywords**: входять в обсяг.
   - `CONTRIBUTING.md`, розділ 1: у `plugin.json` указуємо `keywords` англійською та українською, наприклад `["review", "pull-request", "рев'ю", "код-рев'ю"]`.
   - `validate-marketplace.mjs`: якщо `keywords` відсутні або порожні, показуємо **попередження** (не помилку). Помилка — якщо `keywords` є, але це не масив непорожніх рядків.
   - Компоненти плагіна успадковують його `keywords` у пошуковому індексі ([§4.3](#43-пошуковий-індекс)).
4. **Домен**: стандартний `mshcherbyna.github.io/dev-digest-toolkit-marketplace/`, без `CNAME`.
